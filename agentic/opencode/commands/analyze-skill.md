---
name: analyze-skill
description: 分析一个 SKILL.md（agent skill 定义），产出结构化能力报告
---

分析目标：$ARGUMENTS

如果没有给路径，先问用户要分析哪个 SKILL.md（或 skill 目录）。

## 第一步：读源文件

完整读 SKILL.md。如果 skill 里引用了 `references/` 下的文件（字段模板、错误对照表、checklist 等），这些也要读——很多关键细节只在 references 里，不在 SKILL.md 正文。不要只看 frontmatter 里的 `description` 就动笔。

## 第二步：拆解结构

按下面顺序提取信息：

1. **用途** — 一段话讲清楚这个 skill 端到端做什么，以及支持哪些 connector（CLI / MCP 等），前提是 skill 原文有写。
2. **触发场景** — 从 skill 自己的 `description` / "When to use" 部分摘出用户会怎么说才会触发它。
3. **核心概念** — 用一句话点名整个 skill 教给 agent 的四类东西，格式固定为：「核心来说，Skill 里跟 Agent 说明 `<名词1>`、`<名词2>`...的概念；`<状态机/生命周期/受控词汇体系>`；`<API 字段要求这一层的存在>`；还有 `<核心写操作>` 的 SOP。」四段缺一不可：域概念/对象名词、状态机或受控词汇体系（比如状态标签枚举、固定标题体系）、"skill 里有严格 API 字段规则"这件事本身、以及"skill 教了一套怎么做成这件事的 SOP"这件事本身。只点名，**不展开解释每个词是什么意思，不在这里列举枚举值、不加类比说明**——那些细节留给分阶段流程里对应的步骤去讲，这里只是列"skill 教了这四类东西"。如果 skill 本身以呈现/路由为主、没有实质性核心写操作（比如只读分析类 skill），第四段可以省略，句子在"API 的字段要求"收尾即可，不用硬凑一个写操作出来。如果用途/触发场景段落已经把这些概念名词交代清楚了，这句可以整体不写，不用为了凑格式硬塞一句进去。
4. **前置条件** — skill 在主流程开始前先解决的事（比如某个字段只能问用户拿、环境检查等）。如果 skill 没有这层就跳过。如果 skill 里有一段所有呈现模式共用的数据组装步骤（比如先按顺序查 A、查 B、查 C，供后面各种输出方式使用），这段可以单独列出来讲，也可以直接并进分阶段流程/呈现选择说明的第一步里，不强求单独起标题——哪种读起来更顺就用哪种。
5. **分阶段流程** — 先判断 skill 原文占大头的是"顺序推进的动作步骤"还是"根据情况选呈现格式"：
   - **顺序动作主导**：按 skill 原文自己的结构还原，不要强套成"前置/第一/第二/第三阶段"的固定三段模板。有的 skill 确实是 Phase1/2/3；有的 skill 是别的组织方式（比如"编号步骤 + 输出契约 + 深挖菜单 + 路由表"），这种就按它自己的分节名字和顺序来还原，章节名跟着 skill 原文走。
   - **呈现选择主导**（比如只读分析类 skill，核心是"给定情况，展示哪种分析/报告"）：不用套模板小节，写成一段偏 verbose 的白话说明——有哪些情况/模式、大概对应什么样的呈现内容，讲清楚就够，不用逐字段列成独立小节。跨模式共用的术语/状态标签讲一次即可，不用每个模式重复解释。skill 拒绝/不支持的操作（能力边界类规则）不用单独展开，在"用途"里一句话带过就行。
   - 无论哪种，都要做到：
     - 保留 skill 原文的字段名和 API 值（参数名、合法枚举值、它专门提醒过"长得像但不对"的值），原样带出来，不要转述丢细节。
     - 如果 skill 用了具体数字例子来讲抽象规则（比如"目录里有 N 项，本次操作只涉及其中 M 项，但仍按 N 项全量处理"这种），这种例子要保留，不要压缩成一句抽象规则。
     - 限制/边界自然嵌进对应步骤里讲，不要单独开一个"限制"小节，除非 skill 原文本身就是这么分节的。
6. **收尾/交付步骤** — 核心写操作完成之后发生的事（分享产出、后续提醒、交接给别的 skill），如果 skill 有这一步。

## 第三步：先追问再下结论（默认行为）

写最终报告之前，先用 question 工具问用户 2-4 个针对性问题，确认范围和理解方向。问的方向包括：

- 你理解的用途定位对不对
- 那些偏 API 细节、不好懂的字段/枚举值，要不要专门解释还是一笔带过
- 要不要跟已经分析过的其他 skill 做横向对比（默认不要，单独讲这一个）
- 读源文件时遇到的其他歧义点

除非用户明确说这次跳过追问，否则这一步不能省。

## 第四步：写报告

按下面的形状写（短句陈述，不用加粗小标题堆列表，不用营销词，字段/API 名用反引号包起来，具体数字例子原样保留）：

```
用途：<做什么 + 支持哪些 connector>
触发场景：<用户会怎么说>
核心来说，Skill 里跟 Agent 说明 <名词1>、<名词2>...的概念；<状态机/生命周期/受控词汇体系>；API 的字段要求[；还有 <核心写操作> 的 SOP]。（呈现/路由为主、没有核心写操作，或者用途/触发场景已经交代清楚这些概念的 skill，这句可以整体不写）

前置条件（如适用，也可以并进下面流程/呈现说明的第一步，不强求单独起标题）：
- ...

<顺序动作主导：按 skill 自己的结构分节，用它自己的分节名字，不强套成"第一/第二/第三阶段"；呈现选择主导：写成一段白话，讲清楚有哪些情况对应哪些呈现内容，不用逐字段列成独立小节>
- ...
```

一个语气参考（占位符，不对应任何真实 skill，只示范句子长度和字段引用方式）：

> 匹配已有资源时，`<resource_a>` 按 `<field_x>` 查；`<resource_b>` 的列表接口不支持按名字过滤，只能全量翻页再在客户端比对。只匹配核心场景需要的那类，临时性/一次性的例外一律新建，不去匹配已有资源。

## 第五步：自查

报告写完，逐句核对：

- 每一句能不能在 SKILL.md 原文（或它引用的 references 文件）里找到出处，找不到就删掉或改成"skill 未说明"
- 有没有编造字段名、枚举值、默认值
- 结尾有没有多余的总结句/展望句——如果有，删掉，停在最后一个具体步骤上

## 约束

- 只反馈 skill 文件自己写的内容，不要加自己推断的限制、风险或看法，除非用户明确要这层分析。
- 目标 skill 里如果有"防止 agent 想象/编造/hallucination"之类的通用元规则，这属于 skill 编写规范，不是业务能力，报告不用呈现，聚焦这个 skill 本身承载的业务能力。
- 不主动跟其他 skill 做对比，除非用户要求。
- 不写结尾总结段，停在最后一个具体步骤。
- 报告只在对话里展示，不写文件、不进 wiki，除非用户明确要求。
- 报告是定向导览，不是替代阅读源文件；不用逼着报告面面俱到，细节判断留给读者回源文件确认。
- 跟随当前对话使用的语言，不要写死中文或英文；但如果当前用中文写报告，skill 原文里出现的英文分节标题（比如 `Phase 1: Gather Requirements`）要改写成中文标题，不直接搬英文阶段名。
- 不编造 skill 原文没写的 API 字段或默认值。
- 报告不用「——」「->」这类符号表达停顿、转折或推导关系，这类符号生硬、AI 味重，改用完整短句自然衔接。
- 报告不用 ✅ 等图形符号做标记，保持内容自然可读。
